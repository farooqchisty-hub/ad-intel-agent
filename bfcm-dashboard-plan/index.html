BFCM 2026 live dashboard: implementation plan

Every touchpoint (Meta, Google, email, Intercom, creators, organic) tracked from spend to install, redemption, first paid charge and strategy call. Refreshed every 15 minutes, running on Cloudflare only. Access was verified with live read-only calls on 16 Oct 2026 (IST).

The short version

  • One new Worker, bfcm-dash, with a */15 cron and its own D1. It pulls Meta, Google Ads and GA4 through treg (all three verified today), Intercom, the bfcm-leads D1 (bound read only, no change to that Worker) and a new first-party LP beacon.
  • Dashboard = a static page on GitHub Pages (/bfcm-dashboard/) that reads one aggregates-only endpoint with a view key. Emails and store domains never leave the Worker.
  • Installs are shown through three lenses, never added together: what the ad platform claims, what GA4 sees on the App Store by UTM, and first-party identity (LP email matched to the installed store).
  • Phase 1 ships with access we already have: spend to install, CPI vs $15 / $19, LP funnel, leads and opt-ins, App Store clicks, cohort sizes, paid status, uninstalls, alerts, freshness.
  • What blocks the rest: a redemption event from engineering, a Shopify Partner API client, a Calendly token, and a 2-minute Apps Script on the creator sheet. Google Ads and GA4 need nothing from you.

  • D1 bfcm-dash: facts, identities, daily rollups, 15-min snapshots, source health, alerts
  • Nightly restatement pull (03:30 IST)
  • Alert rules after every rollup
→

Dashboard

  • GitHub Pages ad-intel-agent/bfcm-dashboard/
  • Reads GET /api/summary (aggregates only, view key)
  • Polls every 5 min, shows per-source freshness
  • Optional Slack alert webhook
  • New Worker, not bfcm-leads. bfcm-leads stays the lead-capture and Intercom-tagging Worker (another agent is editing it). bfcm-dash binds its D1 as LEADS_DB for SELECT only and reaches its /admin/list-stats through a service binding. Zero deploys to bfcm-leads.

7. First-party LP beacon

Why: the GitHub Pages LP loads no GA4 or pixel of its own, and the claim events only reach the parent page's dataLayer (no GTM), so GA4 never sees bfcm_claim_click or bfcm_claim_submit. Any direct hit on the GitHub URL (creator links, previews) is invisible today. The beacon fixes both and needs no GA4 access. All events fire from inside the iframe, which already receives the ad's UTMs and click IDs from the Webflow embed, so no Webflow change is required.

Changes in bfcm-lp/claim.py (spec, not built)

  1. CONFIG: add beacon: "https://bfcm-dash.winningstatics.workers.dev/e" next to leadEndpoint.
  2. IDs: SID = 16 random hex per page load; VID = random ID kept 30 days in localStorage (try/catch; Safari partitions storage in iframes, so it falls back to SID).
  3. Sender: bx(ev, extra) posts text/plain JSON via navigator.sendBeacon, with fetch(..., {keepalive:true, mode:"no-cors"}) as fallback, same pattern as the lead post.
  4. One hook for existing events: wrap dataLayer.push in every context (today it is wrapped only when framed) and mirror bfcm_claim_click to cta_click, bfcm_claim_submit to claim_submit, bfcm_chat_open to chat_open.
  5. New events: lp_view once, after the bfcm-params event or 1.5 s (so parent UTMs are merged); scroll_50, scroll_90; claim_box_view via IntersectionObserver at 50% once; email_valid the first time refresh() turns valid (no email content); appstore_click or brevo_click inside claim() before goTop(), plus appstore_click {manual:1} on the "Continue" link; terms_open; exit on the first visibilitychange to hidden, with dwell ms.
  6. Join to leads without touching bfcm-leads: add lp_sid: SID into lead.tracking (stored in the existing tracking_json column) but not into the App Store URL builder.
  7. Join to GA4 installs without identity: when the URL has no utm_id, set utm_id=lp-<SID> on the App Store URL. GA4 then reports shopify_app_install by session manual campaign ID, linking an install to the exact LP session, ad and narrative. Verified with one test install before relying on it.

POST /e in bfcm-dash

  • Accepts only origins https://farooqchisty-hub.github.io, https://www.pushowl.com, https://pushowl.com; 2 KB cap; 30 events per salted IP hash per minute; answers 204 at once, writes in waitUntil.
  • Adds cf.country, device class from UA, and a dc flag when the network is a cloud host (email scanners and link previewers) or the UA is a bot. Flagged traffic is kept but excluded from KPIs by default.
  • Raw events kept 60 days; KPIs live in rollups.

Optional, needs your Webflow sign-in: one line in the Webflow embed that sends parent_view on load and iframe_ready on the existing bfcm-lp-ready message. It measures people who leave before the iframe loads. Nice to have, not required.

Where the UI lives

GitHub Pages, per your rule: farooqchisty-hub.github.io/ad-intel-agent/bfcm-dashboard/. The page is public but holds no data; it fetches /api/summary with a view key taken from the link's #k= fragment (fragments never reach servers or logs) and kept in the browser. Rotating the key revokes old links. Store-level lists (who redeemed, who booked) are not on the page; it links to the matching Intercom tag filter instead. The alternative, Cloudflare Pages behind Access with @brevo.com one-time PIN like CPMA, is stronger but not forwardable to people outside Brevo.
