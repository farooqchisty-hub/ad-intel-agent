PrinciplesWhat makes it durable rather than a find-and-replace.

Config in the database, not the code

Every brand fact lives in tenant config. A CI check fails the build if a PushOwl id or name appears in code again.

Isolation fails closed

Every query and every write carries a tenant. A missing tenant is an error, never "all". The account lock reads the tenant's own accounts.

Holds on by default

A new brand starts with Meta and Google held, goal tracking off and writes read-only, until you switch each on.

Connections are checked, not trusted

Every sync tests each connection's reach and permissions. A lost permission blocks writes for that brand and raises an alert.

No behaviour change for PushOwl

Phase 0 moves PushOwl's values into tenant config and diffs the outputs before and after.

Fair queues

Jobs carry the tenant and run with per-tenant limits, so one brand's backlog can't starve another (the head-of-line trap we already hit).

Health check per sync: can we read the account, the pixel and the conversion event; do we have write scope; does the token expire soon. Any failure sets writes_blocked for that tenant, raises an alert, and shows a Reconnect button.

BackendCloudflare Worker, D1, R2, Queues. Everything still runs in the cloud.

Tenant context

  • Every request resolves a tenant from the x-tenant header (sent by the UI), checked against tenant_users for the signed-in Access email. If no tenant resolves, the request returns 400.
  • The tenant is stored in AsyncLocalStorage (already used by the cost ledger), so deep code can read it without threading a parameter through every call.
  • A db(env) wrapper adds tenant_id to inserts and refuses a SELECT, UPDATE or DELETE on a scoped table that doesn't filter on it. A unit test runs every query string through the same check.

Crons and queues

  • scheduled() lists active tenants and sends one sync and one recommend message per tenant, staggered so they don't all start at once. Every message carries tenantId; consumers set the context first.
  • Run times follow each tenant's timezone (default 09:00 and 17:00 local).
  • Per-tenant concurrency: generation jobs check a per-tenant in-flight count, so one brand's weekly batch can't hold up another's sync.

API

  • GET/POST /api/tenants: list, create (owner only), pause, archive.
  • GET/PUT /api/tenant/config: the config sections, validated against a schema (types, required ids, formats).
  • POST /api/connections/:provider/request, /check, /revoke.
  • Every existing route works unchanged and is scoped by the header.

FrontendThe switch has to be obvious, because acting on the wrong brand is the main risk.

  • Brand switcher in the header: name, logo and a connection dot per platform. The choice is remembered per person and sent on every API call. A coloured band under the header shows the brand at all times.
  • Any action that writes names the brand and the account in its confirm dialog ("Pause ad X on PushOwl · act_…").
  • New tenant settings page: connections and their health, holds, guardrails and autonomy, goals, alert recipients, users and roles.
  • Hard-coded links (Ads Manager, Google Ads) are built from config.
  • Empty states for a new brand: "No data yet: connect Meta", with the next step.
  • An "All brands" overview for whoever runs several brands: spend, cost per conversion against target, open P0 cards and connection health per brand.

Onboarding wizardAbout 15 minutes for the brand, most of it waiting for access to be accepted.

  1. Basics: name, website, product, what a conversion is (install, purchase, lead, signup), currency, timezone, markets and countries.
  2. Meta: Business Manager id → we send a partner request → the brand accepts → we pick up the ad account, page, Instagram account, pixel and conversion event.
  3. Google: customer id → MCC link request → accept → we pick up the conversion actions and flag ones that are secondary or have never fired (the PushOwl lesson).
  4. GA4: property id plus a viewer grant to our service account.
  5. Brand kit: logo, colours, fonts and voice, plus product photos and real UI screenshots from the site or app listing.
  6. Claims: facts they've cleared, each with its source; anything else renders as a visible placeholder.
  7. Competitors: picked from the shared corpus, or swept fresh.
  8. Goals and guardrails: target, ceiling, budget, autonomy; defaults come from 90 days of history once synced.
  9. Review: a checklist of what works and what's missing. The brand is activated with holds on.

Tests that keep it durable

  • Isolation suite: seed brands A and B, run every route and job as A, and assert nothing of B's was read or written.
  • Write-path tests: a write against B's account from A's context must be refused.
  • Query lint: every SQL string touching a scoped table must filter on tenant_id.
  • Hard-code check: a CI grep for account ids, pixel ids, "PushOwl" and "Brevo" in src/.
  • Migration rehearsal on a D1 copy, with row counts compared before and after.

Decisions for you

  1. Meta access model: partner access to our Business Manager (recommended), treg per brand, or the brand's own System User.
  2. Google access model: our manager account (recommended) or treg per brand.
  3. A shared competitor corpus across brands (recommended, cheaper) or a separate one per brand.
  4. Who can create brands, and whether brand users are limited to their brand.
  5. Brevo as the pilot second brand (it replaces the Campaigns tab idea).
